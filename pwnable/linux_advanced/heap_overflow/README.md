# 🧠 Heap Overflow

## 📌 Definition

Heap Overflow = 힙에 할당된 버퍼의 경계를 넘어 인접한 메모리를 덮어쓰는 취약점

메커니즘은 스택 버퍼 오버플로우와 같다. 버퍼 끝을 지나 **낮은 주소에서 높은 주소로 선형으로** 흘러가고, 중간을 건너뛸 수 없다.
다른 것은 **버퍼 뒤에 무엇이 누워 있는가** 하나뿐이다.

- 스택: 호출 규약이 SFP와 리턴 주소를 고정된 자리에 깔아둔다. 타겟이 정해져 있고 카나리가 막는다.
- 힙: 뒤에 오는 것은 **프로그램이 그 다음에 무엇을 할당했는지**에 달려 있다. 타겟을 직접 찾아야 하고, 대신 막는 것도 거의 없다.

---

## 1. 경계는 메모리에 없다

### 메모리는 번호 붙은 바이트 한 줄이다

프로세스 메모리를 칸막이 있는 서랍장으로 상상하면 틀렸다. 정확한 그림은 **번호가 붙은 바이트가 한 줄로 늘어선 테이프**다.

```
0x617040  0x617041  0x617042  0x617043  0x617044  ...
[ byte ]  [ byte ]  [ byte ]  [ byte ]  [ byte ]  ...
```

중요한 건 없는 것이다. "0x617040부터 0x61704b까지는 `src`의 소유"라는 기록이 **하드웨어 어디에도 없다.** CPU는 메모리가 누구 것인지 모르고, 알 필요도 없게 설계되어 있다.

### 배열 접근은 검사가 아니라 덧셈이다

`a[i]`는 다음 한 줄의 주소 산술로 환원된다.

```
주소 = 배열_시작_주소 + (i × sizeof(원소))
```

`int` 배열이면 `a[3]`은 `시작 + 12`, `a[100]`은 `시작 + 400`. 끝이다.
**`i`가 범위를 벗어났는지 확인하는 기계어는 생성되지 않는다.**

```c
int a[3];
a[100] = 1;    // 컴파일 통과. 실행도 됨. 에러 없음.
               // (시작 + 400) 번지에 1을 쓴다. 거기가 누구 땅이든.
```

Python이면 `IndexError`, Java면 `ArrayIndexOutOfBoundsException`이 나지만 C/C++은 그 검사를 **의도적으로 생략**한다. 매 접근마다 비교문을 넣으면 느려지니, "범위는 프로그래머가 지킨다"를 언어 계약으로 삼았다. 이게 메모리 안전성(memory safety)이 없다는 말의 실체다.

### 경계는 숫자 안에만 있다

그럼 평소에는 왜 안 터지는가. 프로그램이 스스로 지키기 때문이다.

```c
for (i = 0; i < size; i++)
    buf[i] = input[i];
         // ↑ 이 숫자 하나가 버퍼를 지키는 유일한 장치
```

`buf`를 보호하는 것은 울타리가 아니라 `size`라는 **숫자**다. 그래서 결론은 이렇게 된다.

> **경계는 메모리에 존재하지 않는다. 경계는 코드가 들고 있는 숫자 안에만 존재한다.**

그리고 오버플로우는 **두 숫자가 어긋나는 사건**으로 정의된다.

```
쓰는 개수  >  버퍼 용량
```

이 부등식을 만들 수 있는 길목을 찾는 것이 분석의 전부다.

## 2. 스택 BOF와 뭐가 다른가

| 항목 | 스택 오버플로우 | 힙 오버플로우 |
|---|---|---|
| 넘친 뒤 바로 나오는 것 | SFP, **리턴 주소** (호출 규약이 고정) | 청크 헤더, **다음에 할당된 객체** |
| RIP를 먹는 경로 | 리턴 주소 덮기 → `ret` | 함수 포인터 / vtable 덮기 → `call` |
| 전용 탐지 장치 | **스택 카나리** | **없음** — 카나리는 힙에 안 깔린다 |
| 터지는 시점 | 함수 리턴 시 (즉시) | **지연** — 나중의 malloc/free에서 |
| 레이아웃 결정 요인 | 컴파일러 (변수 배치) | **런타임 할당 순서** + allocator 정책 |
| 레이아웃 조작 | 거의 불가 | **가능** — malloc/free를 유도해 설계 (heap grooming) |
| 오프셋 구하는 법 | 소스·디컴파일로 계산 | **런타임 실측 필수** |

스택 BOF는 타겟이 정해져 있고 **방어(카나리)가 문제**다. 힙 BOF는 방어가 거의 없는 대신 **타겟을 직접 찾아야** 한다. 난이도의 성격이 "뚫기"에서 "정찰하기"로 이동한다.

그래서 `checksec`에 `Canary found`가 떠 있어도 공격 경로가 힙이면 카나리는 **완전히 무관하다.** 카나리는 스택 프레임의 리턴 주소 앞에만 깔리는 장치이고, 힙 경로는 그 앞을 지나가지 않는다. NX도, Partial RELRO도 경로에 따라 똑같이 무관해진다.

> 보호 기법 표는 경로를 정해주지 않는다. 경로를 정한 뒤에 읽는 참고표다.

## 3. 힙은 어떻게 생겼나

glibc(ptmalloc2) 기준.

### 힙 영역의 출처

- **작은 힙**: `brk`/`sbrk`로 데이터 세그먼트 끝을 밀어내 연속 영역을 확보. main arena가 관리한다.
- **큰 요청** (기본 128KB 이상): `mmap`으로 별도 영역. `IS_MMAPPED` 플래그가 붙고 free 시 바로 `munmap`.
- **top chunk**: 힙 맨 끝의 아직 쪼개지지 않은 덩어리. 재활용할 free 청크가 없으면 **여기서 앞에서부터 잘라낸다.** 이것이 "할당 순서 = 주소 증가 순서"가 되는 이유다.

### 청크 구조

malloc은 요청한 크기만 주지 않는다. **관리용 헤더를 앞에 붙여서** 준다.

```
chunk ptr ─→ ┌────────────────────────────┐
             │ prev_size  (8B)            │  앞 청크가 free일 때만 유효
             ├────────────────────────────┤
             │ size       (8B) + 하위 3비트 플래그 │
             ├────────────────────────────┤  ← malloc()이 반환하는 주소
mem ptr ───→ │   사용자 데이터 (payload)      │
             └────────────────────────────┘
             │ 다음 청크의 prev_size …      │  ← 경계가 맞닿아 있다
```

**`malloc()`이 돌려주는 포인터는 청크의 시작이 아니다.** 청크 시작보다 **16바이트 뒤**다. 오프셋 계산에서 가장 흔한 실수 지점.

### size 하위 3비트는 플래그

청크 크기는 항상 16의 배수라 하위 4비트가 비어 있다. glibc는 그 중 3비트를 쓴다.

| 플래그 | 의미 |
|---|---|
| `PREV_INUSE` (0x1) | 물리적으로 앞 청크가 사용 중이면 1. 0이면 `prev_size`가 유효해져 병합 대상이 된다 |
| `IS_MMAPPED` (0x2) | `mmap`으로 직접 받은 청크 |
| `NON_MAIN_ARENA` (0x4) | main arena가 아닌 arena 소속 |

덤프에서 `0x21`을 보면 "크기 `0x20` + `PREV_INUSE`"로 읽어야 한다. `0x21` 크기의 청크는 존재하지 않는다.

### 정렬과 최소 크기

x86-64에서 청크는 **16바이트 정렬**, **최소 크기 0x20(32바이트)**.

```
chunk_size = max(0x20, align16(요청크기 + 8))
                                      ↑
                     헤더 16B 중 8B만 더한다 —
                     다음 청크의 prev_size 자리를 데이터로 빌려 쓰기 때문
```

| 요청 | 실제 청크 | usable | size 필드 |
|---|---|---|---|
| `malloc(1)` | 0x20 | 24 B | `0x21` |
| `malloc(8)` | 0x20 | 24 B | `0x21` |
| `malloc(12)` | 0x20 | 24 B | `0x21` |
| `malloc(24)` | 0x20 | 24 B | `0x21` |
| `malloc(25)` | 0x30 | 40 B | `0x31` |
| `malloc(40)` | 0x30 | 40 B | `0x31` |

`malloc(8)`, `malloc(12)`, `malloc(24)`가 **전부 같은 0x20 청크**다. 그래서 크기가 다른 작은 객체들이 **32바이트 간격으로 나란히** 깔리는 일이 아주 흔하다. 멤버 하나(8바이트)뿐인 C++ 객체도 32바이트를 차지하고, `int` 3개짜리 벡터 버퍼(12바이트)도 32바이트를 차지한다. **"간격 0x20"은 힙 문제에서 가장 자주 나오는 숫자다.**

### free 청크는 데이터 자리를 포인터 저장소로 쓴다

청크가 free되면 사용자 데이터 자리는 의미가 없으므로 allocator가 거기에 연결 리스트 포인터를 써 넣는다. tcache/fastbin은 `fd` 하나, smallbin/largebin은 `fd`/`bk`.

```
mem ptr ───→ │ fd  ← 다음 free 청크 포인터   │  덮으면 malloc을 속일 수 있다
             │ key ← tcache 소속 표식 (2.29+) │  double free 탐지용
```

여기서 중요한 사실 하나. **사용자 데이터와 allocator 메타데이터가 같은 메모리를 공유한다.** 그래서 "데이터를 덮는 것"과 "메타데이터를 덮는 것"이 물리적으로 구분되지 않는다. 이 설계가 힙 익스플로잇의 토양 전체다.

## 4. 왜 오프셋이 고정인가

힙은 런타임에 결정되는데 왜 오프셋을 상수로 박아도 동작하는가. **절대 주소**와 **상대 거리**를 구분해야 한다.

### 상대 거리는 결정론적이다

ASLR이 켜져 있어도 힙 **내부**의 배치 순서는 할당 코드가 결정한다. 같은 입력이면 같은 malloc 호출 순서가 나오고, allocator는 결정론적이므로 **청크 사이의 상대 거리는 매 실행마다 같다.**

```c
A = malloc(12);   // 0x...020
B = malloc(12);   // 0x...040   (A + 0x20)
C = new Obj();    // 0x...060   (B + 0x20)   ← 이 간격은 실행마다 같다
```

익스에 필요한 것은 대개 절대 주소가 아니라 이 거리뿐이다.

### 절대 주소는 상황에 따라 다르다

- **No PIE**: 바이너리가 `0x400000`에 고정 로드되고 `brk` 힙이 그 바로 뒤에 붙는다. 결과적으로 **힙 절대 주소마저 고정**되는 경우가 많다 → 힙 leak 불필요.
- **PIE**: 힙 베이스가 랜덤화된다. 힙 주소를 써야 하면 **leak 1회**가 필요하지만, 상대 거리는 여전히 고정이라 하나만 leak하면 나머지는 산술로 구한다.

### 레이아웃이 흔들리는 요인

| 요인 | 효과 |
|---|---|
| 이전 free | top chunk가 아니라 재활용분이 반환된다. tcache는 **LIFO**라 free 순서가 할당 주소를 바꾼다 |
| realloc / 컨테이너 증가 | `vector`가 capacity를 넘으면 **새 버퍼를 할당하고 옛 버퍼를 free**한다. 데이터가 이사하고 free 청크가 하나 생긴다 |
| stdio / iostream 초기화 | `printf`, `cout` 첫 사용 시 버퍼를 malloc한다 |
| `tcache_perthread_struct` | glibc 2.26+에서 **힙의 첫 청크**(0x290)로 자동 할당된다 |
| 스레드 | 스레드별 arena가 따로 생겨 전혀 다른 영역에 할당된다 |

> 오프셋은 추측하지 않는다. 계산한 뒤 반드시 디버거로 검증한다. 힙 문제에서 "대충 이쯤"은 100% 틀린다.

## 5. 오버플로우를 만드는 코드 패턴

전부 `쓰는 개수 > 버퍼 용량`을 만드는 방법들이다.

### A. 길이를 source가 정하고 dest 용량을 안 본다

가장 흔하다. 다음 함수군은 **경계 책임을 호출자에게 떠넘기도록 설계**되어 있다.

```c
memcpy(dst, src, src_len);              // dst 용량 인자가 아예 없다
strcpy(dst, src);                       // src의 NUL까지 전부 복사
sprintf(dst, "%s", src);                // 길이 제한 없음
std::copy(src.begin(), src.end(), dst.begin());
                                        // 출력 범위의 '끝'을 받지 않는다
```

**인자를 세어보는 습관**이 여기서 결정적이다. `std::copy`의 3-인자 버전은 입력 범위 `[first, last)`와 출력 **시작점**만 받는다. 출력의 끝이 인자에 없다는 것은 "담을 자리가 있는지는 호출자가 보장하라"는 계약이고, 그 보장 코드가 없으면 그게 취약점이다. `memcpy`와 논리적으로 동일한 버그가 C++ 컨테이너 문법으로 포장된 형태다.

### B. 개수와 버퍼가 서로 다른 객체에서 온다

단일 객체 안에서는 size와 버퍼가 항상 일치한다. `vector::resize`는 숫자와 버퍼를 같이 갱신하므로 혼자서는 절대 안 넘친다. 어긋남은 **두 객체가 섞일 때만** 생긴다.

```c
copy(A.begin(), A.end(), B.begin());
write(B.buf, A.len);
for (i = 0; i < A->count; i++) B->buf[i] = ...;
```

그래서 소스를 볼 때 **두 개 이상의 버퍼를 동시에 인자로 받는 함수**를 전부 의심 목록에 올리고, 각각에 "한쪽의 숫자로 다른 쪽 버퍼에 쓰는가"를 묻는다.

### C. 정수 문제로 길이 검사를 무력화

```c
// C-1. size_t 언더플로우
if (len <= cap) memcpy(buf, src, cap - len);   // len > cap 이면 거대한 값

// C-2. signed → unsigned 변환
int n = get_int();
if (n < MAX) memcpy(buf, src, n);              // n = -1 → 0xffff...ffff

// C-3. 곱셈 오버플로우
p = malloc(count * size);                      // 곱이 wrap → 작은 버퍼
for (i = 0; i < count; i++) p[i] = ...;        // 원래 개수만큼 쓴다
```

C-3이 특히 중요하다. **할당 크기 계산식과 쓰기 루프 상한식이 다르면** 언제든 어긋날 수 있다. (`calloc`은 이 곱셈을 검사한다.)

### D. off-by-one

```c
for (i = 0; i <= size; i++) buf[i] = ...;   // 1칸 초과
buf[strlen(s)] = 0;                         // NUL 1바이트 초과
```

고작 1바이트지만 힙에서는 치명적일 수 있다. 다음 청크 `size` 필드의 **최하위 바이트**를 건드리기 때문이다. `PREV_INUSE`를 0으로 만들면 allocator가 "앞 청크는 free"라고 믿고(poison null byte 계열), 크기를 키우면 다른 청크와 겹치는 overlapping chunk가 만들어진다.

### 탐색 체크리스트

1. 입력 지점(`read`, `scanf`, `cin`, `recv`)을 전부 나열한다.
2. 그중 **값이 아니라 크기·개수·인덱스를 받는 것**에 밑줄을 친다. 거의 항상 여기가 출발점이다.
3. 그 숫자가 흘러가는 경로를 추적해 **경계 검사 없는 복사/루프**에 닿는지 본다.
4. 복사 함수의 **인자 개수**를 세어 출력 용량을 받는 인자가 있는지 확인한다.
5. 할당 크기 계산식과 쓰기 루프 상한식이 **같은 식인지** 비교한다.

## 6. 넘치면 뭐가 덮이나

```
← 쓰기 방향: 낮은 주소 → 높은 주소. 중간을 건너뛸 수 없다 →

[ 내 버퍼 ][ 청크 헤더 ][ 인접 객체 ][ 그 다음 청크 ]
  합법 영역   ② 메타데이터   ①③ 데이터/포인터
```

### ① 인접 객체의 데이터 필드

RIP를 바로 먹지는 못하지만 **다른 취약점을 만들어내는** 가장 안정적인 수단이다. allocator를 건드리지 않으므로 터질 위험이 없다.

- **길이·크기 필드**: 다른 객체의 `len`/`size`/`capacity`를 키워 **더 긴 읽기·쓰기**를 얻는다. 전형적인 권한 상승 사다리.
- **인덱스·카운터**: 배열 접근 인덱스를 키워 OOB로 전환.
- **플래그·권한 비트**: `is_admin`, 상태 머신 변수를 뒤집어 로직 우회.
- **데이터 포인터**: 객체가 들고 있는 버퍼 포인터를 바꿔 **임의 주소 읽기/쓰기(AAR/AAW)** 로 승급. 여기까지 가면 사실상 끝이다.

### ② malloc 메타데이터

`size`, `prev_size`, free 청크의 `fd`/`bk`를 덮어 **allocator 자체를 속인다.** 강력하지만 glibc 버전마다 검사가 달라 까다롭고, 실패하면 abort로 죽는다.

### ③ 인접 객체의 코드 포인터

**함수 포인터, C++ vtable 포인터, 콜백 구조체.** 덮는 즉시 RIP가 내 것이 되는 가장 짧은 경로.

> **우선순위는 ③ → ① → ②.** ②는 다른 길이 없을 때 꺼내는 카드다. 초보자가 가장 많이 하는 실수가, ③이 바로 옆에 있는데도 "힙 문제니까 tcache poisoning"부터 꺼내는 것이다.

### 길에 놓인 것을 복원해야 한다

타겟이 ①이나 ③이어도 거기까지 가는 길에는 **반드시 ②(청크 헤더)가 끼어 있다.** 선형 쓰기는 중간을 건너뛸 수 없으므로 헤더를 지나가며 뭉갠다.

- 덮은 뒤 **malloc/free가 한 번도 호출되지 않고** 바로 타겟이 사용된다면 뭉개진 헤더는 문제를 일으키지 않는다.
- 이후 malloc/free가 일어난다면 **원래 헤더 값을 복원해서 써야** 한다. 보통 `0x21`, `0x31` 같은 값이고, 디버거 덤프에서 원본을 읽어다 쓰는 것이 정석이다.

## 7. 함수 포인터와 vtable

"RIP를 가져온다"를 메모리 수준으로 번역하면 **CPU가 점프 목적지를 메모리에서 읽어오는 순간을 노린다**는 뜻이다. 그런 순간은 세 종류뿐이다.

| 후보 | 어디 사는가 | 발동 | 힙 쓰기로 닿나 |
|---|---|---|---|
| 리턴 주소 | 스택 | `ret` | ✗ |
| GOT 엔트리 | 데이터 섹션 (`.got.plt`) | `jmp *GOT` | ✗ |
| **함수 포인터 / vtable** | **어디든. 힙 포함** | `call *reg` | **✓** |

여기서 중요한 추론이 나온다. **능력이 "힙 쓰기"로 한정되면 앞의 두 후보는 자동 탈락한다.** 기법이 어려워서 포기하는 게 아니라, **능력이 물리적으로 닿지 않아서 애초에 후보가 아니다.** 그래서 카나리와 RELRO를 아무리 들여다봐도 길이 안 보인다.

### 왜 함수 포인터가 최고의 타겟인가

- **간접 비용 0**: leak 없이, ROP 체인 없이, 주소 하나만 쓰면 끝.
- **NX 무관**: 코드를 주입하는 게 아니라 이미 존재하는 코드로 점프한다.
- **카나리 무관**: 스택 프레임을 건드리지 않는다.
- **발동 시점이 명확**: 다음 호출에서 즉시. 루프 안이면 바로 다음 턴.

### C++에서는 공짜로 생긴다

virtual 함수가 하나라도 있으면 컴파일러가 객체 맨 앞에 `vptr`을 자동으로 심는다.

```
객체 (obj ptr)
  +0x00 │ vptr ──────→  vtable  ┌ +0x00 &Foo::~Foo
  +0x08 │ 멤버 1                 │ +0x08 &Foo::method_a
  +0x10 │ 멤버 2                 └ +0x10 &Foo::method_b

obj->method_a();  →  mov rax,[obj]      ; vptr 로드   ← 여기를 덮으면
                     call [rax+0x08]    ; vtable에서 꺼내 호출
```

공격은 두 가지다. **(A) vptr을 가짜 테이블로 돌린다** — 쓰기 가능한 곳에 함수 주소 배열을 깔아두고 vptr을 거기로. **(B) vtable 자체를 덮는다** — 보통 `.rodata`라 읽기 전용이어서 대개 불가. 실전은 거의 항상 (A)다.

virtual이 없는 클래스라면 `vptr`이 없지만, 멤버로 선언된 함수 포인터(`void (*fp)(void)`)가 정확히 같은 역할을 한다. 이쪽이 더 쉽다 — 가짜 테이블 없이 **주소 하나만 쓰면 되기 때문**이다.

### 어디로 점프할 것인가

| 선택지 | 조건 |
|---|---|
| 원샷 가젯 (`getshell`, `win`) | CTF에 심어져 있으면 그걸 쓴다. No PIE면 leak조차 불필요 |
| `system("/bin/sh")` | 인자(`rdi`)를 통제할 수 있어야 한다. 호출 직전 레지스터를 확인해야 쓸 수 있다 |
| one_gadget | 레지스터 전제조건(constraints)이 있다. libc leak 필요 |
| 스택 피보팅 | 인자 통제가 안 되면 `leave; ret` 류로 스택을 옮겨 ROP로 전환 |

## 8. 메타데이터 손상 계열

인접 객체에 쓸모 있는 게 없을 때 꺼내는 카드. **allocator를 속여 "malloc이 내가 원하는 주소를 반환하게" 만드는** 기법군이다. 지도만 그려둔다.

| 기법 | 요지 |
|---|---|
| tcache poisoning | free 청크의 `fd`를 임의 주소로 덮어 다음 `malloc`이 그 주소를 반환하게. 전제: **free된 청크에 쓸 수 있어야** 한다(UAF, double free) |
| safe-linking | glibc 2.32+는 `fd`를 `(주소 >> 12) XOR 실제값`으로 난독화. poisoning 전에 **힙 주소 leak**이 필요해졌다 |
| fastbin dup | 같은 청크를 fastbin에 두 번 넣어 두 포인터가 같은 메모리를 가리키게 (= 인공 UAF) |
| unsafe unlink | `fd`/`bk`를 조작해 병합 시 `unlink`가 임의 쓰기를 하게. 현대 glibc는 `fd->bk == P` 검사로 차단 |
| house of force | top chunk `size`를 `-1`로 덮어 임의 크기 요청으로 top을 원하는 곳까지 밀어낸다. 2.29+에서 차단 |
| overlapping chunks | 청크 `size`를 키워 두 할당이 같은 메모리를 공유하게. off-by-one과 궁합이 좋고 검사를 덜 건드려 안정적 |
| poison null byte | 1바이트 NUL 오버플로우로 `PREV_INUSE`를 지워 잘못된 병합을 유도 |

> 이 기법들은 모두 **"쓰기 권한이 없어서 미래의 malloc을 속여 권한을 얻는"** 우회로다. 이미 직접 쓰기 능력이 있다면 쓸 이유가 없고, 전제조건(UAF 등)도 대개 성립하지 않는다. 순서는 항상 **가진 primitive → 타겟 → 닿는가**이고, 닿지 않을 때 비로소 이 장을 펼친다.

## 9. 왜 힙은 조용한가

같은 "버퍼를 넘쳤다"인데 스택은 `*** stack smashing detected ***`로 즉시 죽고, 힙은 아무 말 없이 지나가는 경우가 많다.

### 카나리는 힙에 없다

스택 카나리는 컴파일러가 **함수 프롤로그/에필로그에 삽입**하는 코드다. 지역 버퍼와 리턴 주소 사이에 난수를 깔고, 리턴 직전에 값이 그대로인지 비교한다. 이게 가능한 건 **스택 프레임 구조가 컴파일 타임에 고정**이고 **검사 지점(리턴)이 명확**하기 때문이다.

힙은 둘 다 성립하지 않는다. 어떤 객체가 어떤 객체 옆에 올지는 런타임에 결정되고, "언제 검사해야 하는가"라는 자연스러운 시점도 없다. 그래서 **힙 객체 사이에는 카나리가 깔리지 않는다.**

### 탐지가 지연된다

힙 오버플로우의 탐지는 allocator가 **그 메타데이터를 다시 읽는 순간**에나 일어난다. 즉 다음 `malloc`/`free`까지 미뤄진다.

```
malloc(): invalid size (unsorted)         size 필드가 깨졌다
malloc(): memory corruption               bin 링크 불일치
free(): invalid next size (fast)          다음 청크 size가 비정상
free(): double free detected in tcache 2  tcache key 중복
corrupted size vs. prev_size              양방향 크기 불일치
munmap_chunk(): invalid pointer           정렬/플래그 이상
```

실전에서 이 메시지들은 **디버깅 단서**로 읽어야 한다. "어떤 검사를 통과하지 못했는가"가 곧 "무엇을 더 그럴듯하게 위조해야 하는가"다. 그리고 **덮은 뒤 malloc/free 전에 타겟이 사용되면 이 검사들은 전혀 작동하지 않는다.** 그래서 "헤더를 뭉갰는데도 익스가 되는" 상황이 생긴다.

## 10. 접근 순서

기법 이름에서 시작하지 않는 것이 핵심이다. 기법은 결론이고, 결론부터 고르면 거의 항상 틀린 길로 간다.

**1. 이기는 순간을 정의한다 (끝에서 거꾸로)**
"이 프로그램이 셸을 띄우는 순간은 정확히 어떤 상태인가?" 목표를 메모리 상태로 번역해둔다.

**2. 입력 지점과 "크기를 받는 곳"을 찾는다**
값은 내용물이지만 **크기는 쓰기 범위의 주인**이다.

**3. 버그를 찾고 능력으로 번역한다**
기법 이름이 아니라 능력을 한 문장으로. 예: *"dest 버퍼 시작점부터 내가 정한 개수만큼 임의의 4바이트 값을 연속해서 쓸 수 있다."* 이 문장이 이후 모든 판단의 기준이 된다.

**4. 타겟을 찾는다**
능력이 닿는 범위 안에서 ③→①→② 순으로. **"내 능력이 물리적으로 닿는가"** 로 후보를 먼저 걸러낸다.

**5. 보호 기법을 점검한다 (여기서 처음 checksec)**
정해진 경로에 대해서만. 대부분의 항목은 경로에 따라 무관해진다.

**6. 남은 미지수를 적고 그것만 측정한다**
보통 한두 개로 좁혀진다 — 대개 오프셋. 소스로는 안 나오니 **그래서** 디버거를 켠다. "일단 둘러보자"가 아니라 질문을 들고 가는 것이다.

**7. 제약을 나열하고 페이로드를 조립한다**
쓰기 단위가 타겟보다 작은가 / 엔디안 / 값 제약(필터, signed 범위) / 길에 놓인 메타데이터 복원 / 발동 시점.

**8. 로컬 성공 후 원격으로**
libc 버전이 다르면 오프셋과 allocator 동작이 달라진다.

> **가장 흔한 실패**: 코드 포인터를 덮으면 그 함수가 더 이상 원래 일을 하지 않는다. 메뉴 출력 함수 포인터를 덮었다면 **메뉴 프롬프트가 더는 나오지 않는다.** 그런데 하네스는 여전히 프롬프트를 기다리고 있어서 영원히 블록된다. **익스는 성공했는데 실패처럼 보인다.**

## 11. 측정 (pwndbg)

```bash
heap                 # 모든 청크를 순서대로 — 주소, size, 상태
vis_heap_chunks      # 청크 경계 시각화 — 가장 직관적
bins                 # tcache, fastbin, unsorted, small, large

x/20gx 0x617040      # 8바이트 단위 20개
x/40wx 0x617040      # 4바이트 단위 40개 (int 배열 볼 때)
x/20gx 0x617040-0x10 # 청크 헤더부터 보려면 16바이트 앞에서
telescope 0x617040 20

search -p 0x400f83   # 이 값이 저장된 곳을 전부 찾는다 (함수 포인터 역추적)

p/d 0x617060 - 0x617040        # 거리 (바이트)
p/d (0x617060 - 0x617040)/4    # int 인덱스
```

### 워크플로

1. **계산 먼저** — allocator 규칙으로 간격을 예측한다. 작은 객체끼리면 보통 `0x20`.
2. **버퍼 주소 확보** — 취약 지점에 브레이크를 걸고 내 버퍼 시작 주소를 읽는다.
3. **타겟 주소 확보** — 주변을 덤프해 **알고 있는 값**(원래 함수 주소, 매직 넘버)을 찾는다. `search`도 좋다.
4. **차이를 쓰기 단위로 나눈다** — `int` 쓰기면 ÷4.
5. **길의 원본 값을 기록** — 지나갈 청크 헤더 값을 적어둔다.
6. **검증** — 패딩만 채워 덮은 뒤 다시 덤프해 경계가 맞았는지 확인한다.

> 오프셋을 찾을 때는 `0x11111111`, `0x22222222` 같은 **식별 가능한 패턴**이나 `cyclic()`을 쓴다. 덤프에서 어느 값이 어디 떨어졌는지 역으로 읽으면 계산 없이 오프셋이 나온다. 0으로 채우면 아무것도 안 보인다.

## 📝 Key Takeaways

- 경계는 메모리에 없다. **코드가 들고 있는 숫자 안에만** 있다.
- 오버플로우 = `쓰는 개수 > 버퍼 용량`. 단일 객체 안에서는 어긋나지 않는다. **개수와 버퍼가 다른 출처에서 올 때**를 의심한다.
- 스택 BOF와 메커니즘은 같고 **이웃이 다르다.** 힙에서는 이웃을 할당 순서가 결정한다.
- `malloc`이 주는 포인터는 **청크 시작이 아니라 16바이트 뒤**다. x86-64 최소 청크는 `0x20`이고 작은 객체는 흔히 **0x20 간격**으로 깔린다.
- 사용자 데이터와 allocator 메타데이터는 **같은 메모리를 공유한다.**
- 절대 주소는 랜덤일 수 있어도 **상대 거리는 결정론적**이다. 익스에 필요한 건 대개 거리다.
- RIP 후보는 셋 — 리턴 주소, GOT, 함수 포인터/vtable. **힙 쓰기로는 세 번째만 닿는다.** 능력이 후보를 걸러낸다.
- **힙에는 카나리가 없다.** `Canary found`는 힙 경로에 무의미하다. 탐지는 다음 malloc/free까지 지연된다.
- 기법에서 시작하지 않는다. **가진 primitive → 타겟 → 닿는가 → 안 닿을 때만 간접 기법.**
- `checksec`은 경로를 정한 **뒤에** 읽는다.
- 오프셋은 계산하고 **반드시 실측한다.** 디버거는 미지수 하나를 재려고 켠다.
- 코드 포인터를 덮으면 **원래 기능이 사라진다.** 익스 성공이 실패처럼 보이는 가장 흔한 함정이다.
